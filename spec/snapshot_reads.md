# Opt-in authenticated snapshot reads

`Authority.read_snapshot(name)` reads a committed metadata snapshot through a separate SQLite connection in URI read-only/query-only mode and a deferred `BEGIN`. The existing `read(name)` remains the serialized default and the comparison baseline. Admission, source validation inside repair, fences, claims, workers, promotion and reclamation retain their existing paths.

SQLite WAL supports simultaneous readers and a writer, and a reader's metadata snapshot excludes uncommitted changes. See the primary [SQLite isolation documentation](https://www.sqlite.org/isolation.html) and [query-only pragma documentation](https://www.sqlite.org/pragma.html#pragma_query_only). This conventional database facility does not version the external pool files.

The content identity, coding profile, length and row digests are immutable after fixture import is sealed. Snapshot reads use the same `_valid_rows` checks as serialized reads: online LIVE rows in the snapshot, profile/row bounds, each expected row digest and slot digest, coherent reconstruction, padding, complete regenerated-row digests and original content digest. Every successful return must equal the snapshot's immutable content. No checksum, floor, fence or receipt check in repair is removed or cached by this feature.

A slot that was LIVE in the snapshot can be retired, reclaimed and reused while physical bytes are being read. The read does not pin slots or block those transitions. If the bytes fail reconstruction or authenticity checks, `read_snapshot` closes the read transaction and calls the existing serialized `read` once. A placement race can then be resolved using current metadata; persistent corruption, unavailable content or unknown identity still rejects. Other database/I/O failures propagate; no unbounded retry occurs. This fallback can block behind repair and has the existing ten-second SQLite busy timeout. Authentic bytes read before a subsequent overwrite still represent the original immutable content and may be returned.

The operation observes online/offline state at its first metadata read, rather than waiting for a concurrent mutation to finish. A domain going offline after that snapshot does not retroactively invalidate already authenticated bytes. Snapshot reads make no latest-placement or mutable-content guarantee. Caller bypass of the API, hash collisions, malicious metadata edits and root replacement are outside the established trusted-local assumptions.

Read transactions are short and closed on success or exception. They can temporarily retain WAL history and compete for CPU/disk even without the writer lock. Opening an `Authority` still performs additive migration under the writer lock before reads begin. This is opt-in pending measurement, and is applicable equally to a conventional cached controller; any measured improvement is not a selective-continuation advantage or coding novelty.
