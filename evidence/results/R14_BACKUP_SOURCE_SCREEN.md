# R14 backup: bounded-journal repair during concurrent writes

Execution: 13–14 October 2026; recorded 14 October. This closes the backup **source-screen task**, not an implementation or a legal rejection of every mutable-repair protocol. The [redesign plan](../../RCSD_PRISM_C_Redesign_Plan.md) requires a concrete distinction before adopting this backup. No such update/retention algorithm has been specified that defeats the following competent construction.

Conventional construction to defeat: authenticate a committed version, retain/checkpoint versions or deltas needed by unfinished repair, index necessary log ranges, apply affected-row updates, publish a version-consistent manifest, collect logs only after completeness/retention conditions, and enforce headroom through admission/backpressure. Give both paths identical write acknowledgements, snapshots, retained versions, repair progress, faults and physical budgets.

The remaining question is a **specific** journal/repair interaction with a supported technical effect beyond this construction. “Mutable content + delta patch + pinned log + resource certificate” does not answer it. Rejected writes or increased reserve cannot masquerade as speedups. No universal impossibility of compact/coalesced journals is claimed.

**Decision:** backup is NOT READY for candidate implementation. This stronger source/combination map partially resolves the Chinese-patent retrieval gap. It establishes neither exact anticipation nor a new surviving mechanism, and awards no points. Native implementations, unbounded proofs, external reproduction and final legal review remain outside the completed task.
