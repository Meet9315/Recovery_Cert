# Interrupted recovery mechanism gate, milestone 11

Registered before comparison collection, 12 October 2026. This is an untimed capability comparison, not a CPU, restoration-latency or patentability confirmation.

The hypothesis is that checked successor admission can retain authenticated staging following a failed destination. First give a conventional partial-state assignment planner the same ability to retain matching staged/reserved rows, discard blocking partial allocations, preserve the live safety floor, and redirect repair into a spare destination. Both conventional cached and selective modes use that planner and the same revision admission, bytes, claims and worker barriers.

Run three seeds (20261012–20261014) for each of two profiles (2+1, 4+2) and both local/worker I/O: 12 pairs, 24 fresh stores. Reverse mode order on alternating seeds. Every store uses 1024-byte slots and two 1025-byte repair objects, plus an independently authenticated foreground object. Reserve all planned destinations, stage the first healthy row, mark destination X offline, and generate a checked replacement using fallback Z. Install a successor with a fresh identity, execute, and compare exact readback and failed-storage charges. Do not compare against a cancel-and-rebuild controller as the primary baseline.

Save complete witnesses, state/ledger snapshots, events, controller rejections and readback results for all attempts, including failures. Compare witness digests, the committed action sequence for the successor, number of authenticated retained staged rows, committed stage bytes, terminal fingerprint and charged offline bytes. Slot bytes represent managed extents; row bytes represent reconstructed fragments. Neither is a measurement of total read/write traffic. A committed stage count excludes repeated unacknowledged worker writes; race/duplicate-write behavior is covered by correctness tests rather than these no-pending-intent fixtures.

An advantage attributable to selective validation is supported here only if it retains more authenticated useful work or avoids more committed repair operations under equal baseline capabilities. Exact equality rejects this work-retention mechanism as a differentiator **for these fixtures**. Equality does not prove equal CPU cost, or rule out all other future mechanisms. The previously stated 20% verification CPU, 10% secondary improvement and 5% foreground limits cannot be passed by this untimed gate. If no differentiating operation is found, do not run a large confirmation campaign or increase the rating based on this feature.

Report the independent 40-case partial-state matrix separately; its single-stripe grammar and finite budgets do not prove arbitrary completeness or global minimum repair traffic. Freeze implementation/protocol in Git before collection and record source, script, protocol and commit identities in the report. The full regression runner remains separate from performance interpretation.
