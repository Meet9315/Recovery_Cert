# Registered fault/retry and scoped-contention comparison — version 1

Freeze this protocol, benchmark helpers and tests in Git before collecting the milestone 10 campaign. Seed 20261012; ten measured pairs per configuration; one excluded, retained warmup per mode/configuration. Randomized mode order within each pair. No outlier trimming, replacements or dropped partial attempts. Save after every attempt and preserve all failures.

Four configurations: fixed 2+1 and 4+2 profiles, each with (a) lost-receipt retry and (b) scoped contention. Two 1025-byte immutable stripes, 1024-byte slots; identical content, destinations, conventional scheduler, scoped witnesses, worker processes, authenticated read reuse and snapshot read probes in `conventional_cached` and `selective`. Initial stripe 0 destinations are retired; stripe 1 destinations are free. Claims use disjoint slots in shared source/destination domains. Fixture creation, worker initialization, planning/admission and controller startup/barrier readiness are outside restoration timing.

Lost-receipt retry: one controller repairs both admitted scopes sequentially. At its first stage, the worker commits/fsyncs its normal durable receipt and then actually calls `os._exit(77)` before returning it. The authority cursor and capacity charge must remain unchanged. Same-epoch preparation must reuse the token; duplicate execution must return the exact committed receipt before checked completion. No controller restart, takeover, power loss or hardware failure is represented.

Contention: two separate controller subprocesses, one per scope, start at a common file barrier and compete for the same SQLite authority writer. Preserve process IDs, actual step intervals and pulse observations; shared labels are not independent devices. Simultaneous launch alone does not prove overlapping execution intervals. An authenticated foreground snapshot read follows every repair action in both scenarios; these are correctness probes, not fixed-arrival foreground latency measurements.

Restoration wall time: parent barrier release through collection of every controller's terminal result, including retry, read probes and result serialization. Broad CPU: timed parent CPU + controller CPU from barrier receipt through pulse stop + every worker process CPU from startup/imports through operation/receipt commit, sampled before diagnostic-file write and stdout/exit. The diagnostic write, worker teardown and controller result serialization CPU are excluded, although their wall time is included. Worker calls, including the failed worker and receipt probes, have raw CPU/exit telemetry. Controller/parent startup and fixture/audit CPU are excluded. Instrumentation costs and content probes are included symmetrically. No isolated verification-CPU claim, calibration extrapolation or idle padding; reject missing worker telemetry and retain zero clock observations.

One warmup and ten pairs are independent stores with matched seeds; 40 pairs/80 measured attempts, eight warmups. Report both per-pair reductions `100*(conventional-selective)/conventional` and their mean, 2000 seeded bootstrap resamples and empirical 95% interval (indices 49/1949), separately for CPU and wall time. Existing 20% CPU/10% restoration proxy thresholds are evaluated with the lower confidence bound. They cannot establish the complete controller gate: the foreground 5% gate is not evaluated here; stronger baseline fairness, larger repair workloads and deployment scope remain open.

50 ms controller/parent pulse threads retain raw monotonic/wall/process-CPU samples and all observed gaps of at least 500 ms. Gaps are diagnostic observation delays with unknown cause, never grounds for deleting observations. Raw worker telemetry and controller stdout/stderr are preserved. Reopen each store, audit decoding floor/target, check exact immutable bytes and managed-capacity conservation, and require no active plans. Runtime databases and HMAC secrets stay temporary and untracked. Source hashes, environment and protocol digest accompany raw evidence. Ratings and patentability conclusions do not change from ordinary optimization or this bounded comparison alone.
