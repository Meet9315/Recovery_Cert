# Registered paired immutable-read latency comparison

Version 1 — 12 October 2026. Freeze code, tests and this protocol before collecting confirmation outcomes. Preserve milestones 6/7 and their raw evidence unchanged.

## Question and scope

Compare the existing serialized `Authority.read` with the opt-in `Authority.read_snapshot` under the same competent **conventional_cached** repair controller. Use both fixed coding profiles and local/worker paths: four configurations, ten independently seeded pairs per configuration, eighty completed windows. Randomize API order within each pair using the saved seed. Each API has its own fresh store and no-repair control. This evaluates a conventional immutable-read optimization, not selective-continuation superiority, a coding invention, the original CPU/restoration gate or a new patentability rating. Keep serialized reads the default after this experiment.

## Workload and arrival membership

Reuse the milestone 7 prepared backlog: 64 groups of two stripes, shared source/destination domains, 1,025-byte repair objects, 1,024-byte slots, half the destination slots retired using first-free seeding. Identical bytes, initial metadata fingerprints, eligibility and protection across APIs within each pair. Early groups reclaim both destination slots. Repair one admitted complete whole-stripe scope at a time with the conventional scheduler. The unrelated fully protected foreground object has the same immutable bytes as before. Setup, migration, worker enabling and independent post-run audit are outside the windows.

A spawned reader process contains one arrival producer and one read-service thread. Offer exactly **400 requests per phase at 100 requests/second**, on a fixed monotonic schedule independent of read completions. Record ideal arrival, actual enqueue, service start/end, scheduling lateness, queue delay, service duration, end-to-end latency and error for every offered request. End-to-end latency is end minus ideal arrival and is the primary metric. Queued calls are never silently skipped or replaced with a closed-loop delay. A per-phase queue budget of 400 holds all offered requests; no request is dropped. The producer may enqueue late after OS scheduling delays, and that lateness stays in latency.

Drain all control requests before acknowledging the control-to-load barrier. The parent supplies a shared phase origin, then starts repair and loaded arrivals together. Continue admitting repair groups until all 400 loaded requests have been offered; finish the current admitted group. No post-repair admission or artificial delay is used to collect successes. Stop new repair admission at 20 seconds or backlog exhaustion; either occurring before all arrivals have been offered fails the attempt. Drain **every** loaded request after repair stops, including calls whose service starts after restoration. Phase membership follows scheduled arrival, not service completion/start. Preserve all boundary and post-restoration-service counts. End-to-end p99 uses nearest rank and requires at least 200 successful observations per phase and no errors; confirmation requires all 400 scheduled requests to be offered and completed successfully.

The 100 Hz workload is a fixed diagnostic arrival load, not a measured saturation rate or external network client. The scheduled phase lasts 3.99 seconds plus producer scheduling delay. Parent/group completion and request drain can extend past that. A control drain and final reader collection each have a 60-second timeout; any child, API, target/readback, membership, sample or timeout failure preserves a failed attempt/context and ends the campaign unsuccessfully. On forced termination, raw in-flight records may be unavailable; do not treat a partial attempt as completed or analyze it as a successful pair.

## Integrity and analysis

After reopening, check all original objects, the whole backlog's safety floor, every completed group's target, no active plans and total capacity conservation. Record groups, exact witness digests, durations, initial fingerprint, seed/order, every request and all fallback calls. Group counts can differ across APIs because of the stopping rule; do not interpret CPU/restoration differences from these windows. Snapshot fallback uses the unchanged serialized API; it retains its busy timeout and any error is preserved. Source and protocol SHA-256, environment and clock metadata are saved; checkpoint after each completed API attempt and pair. Warm-up: one two-stripe disposable repair/read per configuration/API, outside confirmation data, with integrity checks.

For each configuration, report all ten paired percent reductions in loaded end-to-end p99: `100 * (serialized - snapshot) / serialized`, and the mean with 2,000 deterministic pair-resampling bootstrap draws (2.5%/97.5% percentile interval). Positive is better. Also report each API's loaded/control p99 inflation and all ten raw ratios. The original foreground condition is no more than **5%** overhead versus that API's own no-repair control. A narrow diagnostic compatibility screen passes only when the upper 95% bootstrap bound of the mean inflation is at most 1.05 for the snapshot API. Preserve failures and mixed outcomes; do not average configurations into a favourable-only overall pass. A reduction versus serialized reads alone does not satisfy the 5% condition. These ten-pair intervals are local estimates, not tail-SLO proof; no familywise correction is applied, and no aggregate research gate is declared.

Report raw scheduling lateness and service costs alongside queue/end-to-end results. Runtime/SQLite/WAL checkpoint effects, CPU contention, request queuing and transient busy fallback remain included. This confirms only this trusted local workload. No fault performance, independent devices, remote daemons, open-ended mutable objects, production deployment or patentability score follows from the result.
