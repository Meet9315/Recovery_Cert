# Registered sampling and CPU-attribution diagnostics

Version 1 — 12 October 2026. Freeze before collecting diagnostic outcomes. Preserve the milestone 6 protocol, command and results unchanged. This is a measurement-development milestone, not a ten-pair performance confirmation or a G6 pass.

## Foreground windows

Use both fixed profiles, local/worker paths and conventional cached/selective/full modes: twelve diagnostic cells, one seeded window per cell. Each store has 64 prepared groups of two repair stripes plus the same fully protected unrelated foreground object as milestone 6. Each repair group uses distinct stripe/source/destination slots in shared domains, with the same 1,025-byte objects, coding protection and half-retired destinations. Admit one complete whole-stripe scope at a time using the conventional scheduler. Fixture construction and worker enabling are excluded. The backlog is identical within each profile/path across modes; previously completed groups stay immutable.

Retired destination slots occupy the first half of each shared domain, following the fixture API's deterministic first-free placement. Early groups therefore reclaim both destination slots; later groups use free slots. "Half retired" describes the entire backlog, not each individual group. This differs from the single-group CPU fixture, which has one retired slot per destination domain. Keep both workload definitions explicit.

One separate spawned reader calls the real `Authority.read` API, verifies exact bytes and offers a new request no sooner than 2 ms after the prior request starts. It does not queue missed arrivals. Preserve every started request's start/end timestamps, starting phase, ending phase, outcome and latency. Errors are retained and prevent healthy/sufficient classification. This is a closed-loop foreground workload, not a saturation or open-loop arrival benchmark.

Control: at least 2 seconds and 400 successful reads, capped at 10 seconds. Pause the reader **after its current call finishes**, acknowledge the pause, and only then start the loaded phase. This prevents repair from contaminating the no-repair control. The transition retains the final control call. Repair load: start new groups while fewer than 4 seconds have elapsed or fewer than 400 successful loaded reads have completed, stopping new admission at 20 seconds or backlog exhaustion. An admitted group finishes; no dummy delay or post-repair idle padding is added to obtain samples. These stopping rules can produce different numbers of completed groups across modes, so no paired CPU/restoration-effect estimate is computed from these windows.

At load completion, stop new foreground requests and drain the one in flight. Every request that started during load remains a loaded observation even if it ends after restoration. Record boundary-spanning counts and raw outcomes. Validate every completed group's target and original bytes after reopening; validate the safety floor of the untouched backlog and conserved capacity. Report stop reason, actual control/load/drain durations, groups completed and sample counts. Nearest-rank p99 requires at least 200 successful reads per phase and no errors; the collection target is 400. Low counts remain insufficient and deadlines/backlog exhaustion are explicit. No 5% threshold is evaluated from these single diagnostic windows.

## CPU attribution

Separately profile one complete two-stripe repair per profile/path/mode: twelve cells with the original milestone 6 fixture and no foreground process. Include planning, admission, equal ledger observations, all actions, physical checks and worker reconciliation. Fixture creation, independent terminal/readback audit and report processing are excluded. Use a `cProfile` custom process-CPU timer; save all per-function primitive/total call counts, exclusive CPU and inclusive CPU. Assign each exclusive function cost exactly once to a declared category. Inclusive costs overlap and must not be summed. Categories include logical replay, continuation certificates, state/model work, coding, hashing, SQLite, file I/O, serialization, worker control/transport and runtime overhead.

Benchmark-only nested spans measure logical verification/certificate APIs, state/witness commitments and claims/fence checking. Count all calls, but add elapsed CPU only for outermost spans, including their nested work. List the wrapped APIs in the report. This is a declared logical-verification subset; snapshot construction, physical source validation, staged-byte validation and durable receipt/payload checking are outside that subset and remain visible in the profiler. Its CPU is another view of the same execution, not a quantity to add to exclusive categories.

Profile worker `handle` calls in the benchmark-only worker envelope. Keep durable commands and receipts unchanged. Report worker-handler exclusive categories and separate whole-worker-process CPU through handler completion, including startup/imports and instrumentation; output/teardown is excluded. Parent CPU does not include child CPU. Profiling and span overhead affect timings, especially small functions; timer quantization may yield zero entries. No speedup, precise production cost share, confidence interval, original 20% verification-CPU pass or patentability score follows from one instrumented cell.

## Evidence and integrity

Record protocol and source SHA-256, seed, actual clock metadata, raw observations and profile entries. Stop and preserve a partial report on controller failure; retain a foreground failure cell with errors and an unsuccessful campaign status. Check all corresponding modes' initial backlog or single-group witness fingerprints. Keep the same baseline, protection guarantees and original research thresholds. A subsequent registered confirmation needs independent paired windows, stronger foreground arrival workloads and fault/retry/scoped-contention evaluation.
