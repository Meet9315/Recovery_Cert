# Registered local controller comparison

Version 1 — 12 October 2026. Freeze this file before collecting comparison results. Its SHA-256 is saved in every report. This extends the logical benchmark to actual durable storage; it is a reduced experiment, not the complete G6 research gate.

## Workloads and comparator

Run both fixed profiles, 2 and 8 repair stripes, and both local and storage-worker paths: eight configurations. Each stripe has 1,025 independently seeded immutable bytes, initially exactly its data-row count. For 4+2, initial rows are 0, 2, 4 and 5, so repair reconstructs missing data rows. Each stripe has distinct slots in shared source domains and one (2+1) or two (4+2) destinations. Half of each destination domain's slots are retired. Use a complete group witness from the conventional matching scheduler for every mode; include planning, admission, all steps and reconciliation in measurement. All modes have identical content, capacity, placement, protection and witness. No faults or cancellations are injected here; those remain correctness regressions and a later performance extension.

Compare the deployed `conventional_cached` baseline, `selective`, and `full` ablation. Use ten independently seeded paired runs per configuration, with a deterministic randomized mode order. Include all configurations and runs, including slowdowns. Warm each mode once per configuration, excluded. Fixture creation/bootstrap, worker enabling and reader startup are excluded and timed separately. Pool slots are 1,024 bytes; use fresh disposable stores for every attempt. No store is reset or reused for another mode.

## Measurements

Primary descriptive metric: combined controller and worker-process CPU per completed group, normalized per repaired stripe. Controller CPU includes planning, persistence, physical checks, decoding, cache work, RPC framing and allocation-ledger observation. Benchmark-only worker envelopes report process CPU through handler completion, including interpreter startup/imports and SQLite/fsync work; final JSON printing and process teardown are excluded. The reader's CPU is separate. This broad CPU metric is a conservative overhead proxy, not isolated verification CPU or system-wide kernel/I/O accounting.

Calibrate the conventional mode, doubling equal-sized batches until measured controller-plus-worker CPU reaches 50 ms, at most eight attempts per batch. Use that same batch size for all three modes. Calibration is excluded and reported. A baseline sample of zero CPU prevents percentage-effect interpretation; report it rather than divide by zero or silently drop a pair. Outer restoration wall time includes all timed operations. **Time to restoration** is the preselected practical secondary metric; temporary capacity is descriptive, not a substitute metric after seeing results.

A separate spawned foreground reader repeatedly calls the real `Authority.read` API for an unrelated, fully protected 2+1 stripe in the same metadata authority. It validates exact bytes. Its target read interval is 2 ms, without queuing missed requests. Collect a 500 ms no-repair control period on that same store, then read during repair. Only calls starting and ending within one phase are counted. Preserve raw latencies, errors and achieved sample counts. Report nearest-rank p99 only with at least 200 observations in **each** phase of an attempt; otherwise label foreground p99 insufficient. This API takes an authority writer transaction, so this measures actual local contention, not a hypothetical nonblocking read implementation. The workload is not a fixed-arrival-rate saturation benchmark.

Observe category capacity after admission and each step, report peak non-FREE managed bytes, promoted payload bytes, reclaim extent bytes and worker RPC counts. These observations add equal harness cost to all modes. Validate ledger conservation throughout; outside the timed interval, independently audit terminal safety, read every original object after reopening, verify no active plan remains, and compare witness/action commitments across modes. Any exception or mismatch stops the run with a preserved partial report; no failed attempt is removed or reported as completion.

## Analysis and limits

Aggregate at the paired-run level, summing equal-sized batches. Report raw attempts, absolute medians, paired percentage reductions and seeded 2,000-resample bootstrap 95% intervals of the mean paired reduction for selective versus conventional and full. Bootstrap instances are not independent experiments. CPU and restoration comparisons require ten complete pairs. Report foreground effects only for sufficiently sampled pairs; never extrapolate missing p99 results.

The project's proposed thresholds remain 20% verification CPU reduction, 10% restoration improvement and at most 5% foreground p99 degradation against the capable baseline. Report whether the broad measured CPU/restoration proxies meet their numerical thresholds, including interval uncertainty; these proxies do not establish the original verification-CPU target. No G6 pass or score change is automatic. Independent devices, foreground saturation, injected-fault/retry performance, aggregate host CPU and full mechanism attribution remain outstanding.
